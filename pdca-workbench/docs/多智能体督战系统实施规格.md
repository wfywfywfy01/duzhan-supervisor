# 海外渠道 PDCA 多智能体督战系统实施规格

> 用途：交给其他代码模型分阶段实现。  
> 仓库：`D:\经销商PDCA`  
> 主应用：`pdca-workbench/`  
> 状态：实施设计，不代表当前功能已经完成。  
> 原则：复用现有业务，不重写督战、C转B、日报、Vemory、VPS、WhatsApp 和 MTO 链路。

---

## 1. 目标

建设一套由五类能力组成的海外渠道 PDCA 系统：

1. **主 Agent（Supervisor）**
   - 接收用户任务、群事件、定时事件和系统告警。
   - 理解任务，补全上下文，拆分子任务并选择执行者。
   - 汇总五个业绩达标群、十六个 C转B 群、海外日报群和会议数据。
   - 输出部门早会、红黑榜、跨群卡点、待管理层拍板事项。

2. **豆包 ASR 服务**
   - 识别经销商会议音频。
   - 输出逐句转写、时间戳、说话人和置信度。
   - 转写结果进入证据库，供群 Agent 和主 Agent 提取任务。

3. **流程控制器**
   - 按时区执行提前采集、10:00、15:00、20:00 三追。
   - 控制 C转B 20:00 晚追、日报、Vemory 待办同步。
   - 处理幂等、重试、超时、补偿、健康检查和告警。

4. **群级 Agent**
   - 每个群有独立逻辑实例和独立状态。
   - 跟踪本群任务、承诺、证据、卡点、下一动作和最终闭环。
   - 五个业绩达标群和十六个 C转B 群复用同一套图，不复制代码。

5. **MTO 视觉能力**
   - 检查群内 MTO 图片、OCR 报价、款式数量和是否达到金额标准。
   - 检查重复图片、缺报价、图片与汇报不一致。
   - 输出结构化证据，不直接作扣罚决定。

### 1.1 成功标准

- 定时任务不依赖聊天会话是否在线。
- 10:00、15:00、20:00 每档都有运行凭证、采集快照和推送结果。
- 每条结论能追溯到群消息、WhatsApp、Vemory/VPS、日报或图片证据。
- 数据缺失时写“待确认”，禁止把 `None` 当 `0`。
- 主 Agent、群 Agent 和专用模型不能绕过审批直接扣罚、改规则或发合同结论。
- 一个群故障不阻断其他群。
- 模型故障不阻断确定性定时任务。

### 1.2 不在本期范围

- 不重写现有 FastAPI、APScheduler 和 PostgreSQL。
- 不引入 Kafka、Temporal、CrewAI、AutoGen。
- 不把每个群部署成独立进程或独立容器。
- 不跨仓直连 `vertu-data-hub` 数据库，只通过私有 API。
- 不自动生成正式法律意见。
- 不自动提交 Git、不自动部署生产。

### 2.4 当前业务约束

- 日报缺失：个人 Check 高风险，并生成补交和组长跟进动作。
- 默认过程指标：新增客户 3、有效触达 15、客户跟进 8、报价 2、重点客户维护 2、日报 1。
- A 类客户超过 7 天未跟进：超期风险。
- B/C 类客户超过 14 天未跟进：超期风险。
- 组长客户占比超过 60%，且有组员客户数为 0：资源失衡。
- MTO 目标：每日 4 款，每款报价不低于 30 万。
- 无数据、接口未覆盖、内容无法识别：写“待确认”。
- 当前无奖励政策。
- 扣罚规则历史上有过调整，**不得直接写死自动扣罚**。上线前需业务负责人确认版本并人工审批。
- 合同、折扣、经销商权益相关输出不是正式法律意见，必须人工复核。

## 3. 总体架构

```text
用户 / 群事件 / 定时事件 / 系统告警
                  |
                  v
             Task Gateway
                  |
       +----------+----------+
       |                     |
       v                     v
确定性命令路由          主 Agent / Supervisor
       |               理解、拆解、分发、汇总
       +----------+----------+
                  |
                  v
       PostgreSQL 任务与事实状态
       run / task / event / outbox
                  |
       +----------+-----------+----------------+
       |                      |                |
       v                      v                v
流程控制器              群级 Agent          专用能力
APScheduler              GroupGraph          豆包 ASR / MTO Vision
       |                      |                |
       +----------+-----------+----------------+
                  |
                  v
              审批 Outbox
                  |
             人工批准 / 拒绝
                  |
                  v
          VPS IM / 日报群 / 告警
```

### 3.1 强制边界

1. **事实只从数据源和状态库读取。**
2. **主 Agent 不直接发群。**
3. **群 Agent 不直接扣罚。**
4. **流程控制器不依赖 LLM 才能按时运行。**
5. **ASR 和视觉是能力服务，不负责业务裁决。**
6. **所有外发先生成 Outbox 记录。**
7. **需要审批的消息只有批准后才能发送。**
8. **定时提醒可以按已确认模板自动发送，但仍需保留 Outbox 和审计。**

## 4. 技术选型

### 4.1 保留

- Web/API：FastAPI。
- ORM/数据库：SQLModel + PostgreSQL。
- 调度：APScheduler。
- HTTP：`httpx`。
- 日志：Loguru。
- 现有 IM 推送：`push_duzhan_message`、`push_vps_message`。
- 现有幂等：`scheduled_job_runs`。

### 4.2 新增

- Agent 状态图：LangGraph。
- Supervisor 模型适配层：供应商无关，模型名由环境变量配置。
- 豆包 ASR HTTP 适配器。
- PostgreSQL Outbox。

### 4.3 暂不新增

- Kafka。
- Redis。
- Celery。
- Temporal。
- CrewAI。
- AutoGen。
- 每群独立容器。

出现以下任一情况后再评估 Temporal：

- 单任务跨服务运行超过数小时且补偿步骤复杂。
- 每日任务量达到现有 APScheduler/PostgreSQL 难以承受。
- 大量异步回调需要跨进程保证 exactly-once。
- 需要可视化重放复杂长事务。

## 7. 主 Agent 设计

### 7.1 职责

- 接收自然语言任务。
- 判断任务是查询、汇总、采集、催办、规则修改、外发还是审批。
- 对模糊任务提出最少必要问题。
- 将任务拆成结构化动作。
- 调用流程控制器、群 Agent、ASR、视觉或只读查询工具。
- 汇总跨群结果。
- 对所有结论附来源。

### 7.2 禁止事项

- 不直接调用底层 IM 推送函数。
- 不直接修改扣罚台账。
- 不从模型记忆生成业绩金额。
- 不把接口错误解释为业务为零。
- 不跨越 `agent_outbox`。
- 不更改 `owner_locked=True` 的任务执行人。

### 7.3 LangGraph 节点

```text
receive
  -> authenticate
  -> classify
  -> load_context
  -> plan
  -> validate_plan
  -> dispatch
  -> wait_results
  -> aggregate
  -> fact_check
  -> approval_gate
  -> persist_result
  -> complete
```

分支：

```text
known_readonly_query -> deterministic query -> aggregate
scheduled_event      -> flow controller，不先调用 LLM
risky_action         -> approval_gate
missing_context      -> ask_user
source_failure       -> blocked / 待确认
```

### 7.4 模型策略

- 模型通过环境变量配置，不在代码写死供应商。
- 主 Agent 使用强模型。
- 只在需要理解、拆解、冲突处理和总结时调用。
- 已知命令使用确定性路由。
- 设置最大工具调用数、最大输入长度和超时。
- 模型失败时保留任务，不允许吞错。

环境变量建议：

```text
PDCA_SUPERVISOR_ENABLED=0
PDCA_SUPERVISOR_PROVIDER=
PDCA_SUPERVISOR_MODEL=
PDCA_SUPERVISOR_API_KEY=
PDCA_SUPERVISOR_TIMEOUT_SECONDS=90
PDCA_SUPERVISOR_MAX_TOOL_CALLS=12
```

### 7.5 上下文装配

主 Agent 每次只加载：

- 当前用户任务。
- 当前日期和请求时区。
- 有关群的最新 slot 快照。
- 未闭环 `pdca_tasks`。
- 当前规则版本。
- 必要的会议/MTO/WhatsApp 摘要。

禁止默认加载：

- 全部历史群消息。
- 全部客户原始资料。
- 无关会议全文。
- 所有群的原始图片。

### 7.6 事实校验

生成部门总结后执行确定性校验：

- 所有金额能在证据或台账中找到。
- 所有人名在注册表中。
- 所有任务有来源。
- `None` 未被转换为 `0`。
- “已完成”必须有 `verification_status=verified`。
- 合同/折扣段落包含人工复核提示。
- 总结中出现“圣诞、黑五、提前备货”等结论时，必须附消息或转写证据。

校验失败：

- 不外发。
- 写入 `agent_events`。
- 主结果标记 `waiting_approval` 或 `blocked`。

### 8.2 每档时序

以北京时间 10:00 为例：

```text
09:45
  claim duzhan_collect:Asia/Shanghai:10:{date}
  读取五群/日报/WhatsApp/Vemory/VPS/MTO
  写 duzhan slot 快照

10:00
  claim duzhan:Asia/Shanghai:10:{date}
  发送已批准/自动模板消息
  写 push_succeeded 或 push_failed

10:05
  健康检查
  缺快照、缺 outbox、发送失败均告警
```

15:00：

- 14:45 采集。
- 对比 10:00 snapshot。
- 只输出完成、推进、停滞、未回复和新增卡点。
- 不重复整段 10:00 计划。

20:00：

- 19:45 采集。
- 对比 15:00 snapshot。
- 核验交付物。
- 未完成任务结转次日第一动作。
- C转B 16 群按现有代码在北京 20:00 运行。

Alice：

- 使用 `Europe/Paris` 独立执行。
- 不把北京时间 10:00 当作 Alice 的 10:00。
- 中英文模板保持现有行为。

### 8.3 健康检查

新增调度：

```text
每档整点后 5 分钟运行
```

检查：

- `scheduled_job_runs` 是否有 collect 记录。
- slot 文件是否存在。
- JSON 是否可解析。
- `prepared_at` 是否属于当天该档。
- 目标群数量是否正确。
- outbox 是否生成。
- 应发送消息是否成功。

告警内容：

```text
日期
时区
档位
缺失步骤
最后错误
建议人工动作
```

今天 10:00 未运行的问题，应由该健康检查在 10:05 自动发现。

### 8.4 失败规则

- 单数据源失败：继续组表，相关字段写“待确认”。
- `collect_ledger` 整体失败：使用 `empty_ledger`，但标记 degraded。
- 快照不存在：现有 `run_duzhan` 可现场渲染；新增告警，不静默。
- 推送失败：最多重试一次；仍失败写 outbox failed 并告警。
- 模型失败：回退现有确定性 `render_brief`。
- PostgreSQL 不可用：禁止推送需要审批的内容；确定性模板是否继续由配置决定。

### 9.2 GroupGraph

### 9.3 任务状态机

```text
pending
  -> assigned
  -> claimed
  -> in_progress
  -> evidence_submitted
  -> verified
  -> done
```

异常分支：

```text
pending -> blocked
in_progress -> blocked
evidence_submitted -> rejected -> in_progress
任何未完成状态 -> overdue
overdue -> escalated
```

闭环定义：

- `claimed`：只表示知情。
- `in_progress`：有动作但无完整结果。
- `evidence_submitted`：提交了证据，尚未核验。
- `verified`：证据与目标一致。
- `done`：核验通过且无剩余动作。

禁止：

- “收到”“好的”“已跟进”直接闭环。
- 只有日报自报、无群/VPS/Vemory/WhatsApp证据时直接判完成。
- 客户未回复时写“已成功”。

### 9.4 达标群职责

- 回款和付款节点。
- 重点客户跟进。
- MTO 数量和报价。
- WhatsApp 触达/回复。
- VPS 留痕。
- Vemory 会议。
- 日报提交。
- 卡点和支持需求。

10:00 输出：

- 当日 3—5 项任务。
- 客户、动作、交付物、截止时间。
- 昨日结转第一动作。

15:00 输出：

- 相对 10:00 的变化。
- 未回复客户。
- 需要中台/领导拍板事项。

20:00 输出：

- 已完成且有证据。
- 未完成原因。
- 次日第一动作。
- 争议项待人工复核。

### 9.5 C转B 群职责

## 10. 豆包 ASR 服务

### 10.1 定位

豆包只做语音识别。任务提取、客户判断、承诺识别交给 Agent 层。

建议新增：

```text
app/agents/asr_doubao.py
app/agents/asr_service.py
tests/test_asr_doubao.py
```

### 10.2 官方接口依据

官方文档：

- [录音文件极速版识别 HTTP](https://docs.volcengine.com/docs/6561/1631584?lang=zh)
- [录音文件结果查询 HTTP](https://docs.volcengine.com/docs/6561/2606792?lang=zh)

当前官方“录音文件极速版”文档说明：

- HTTP `POST https://openspeech.bytedance.com/api/v3/auc/bigmodel/recognize/flash`
- 单次请求返回结果。
- 音频不超过 2 小时、100 MB。
- 支持 WAV、MP3、OGG OPUS。
- 资源 ID 示例：`volc.bigasr.auc_turbo`。

接口和资源 ID可能随账号版本变化，实施时必须以控制台已开通资源为准。

### 10.3 环境变量

```text
PDCA_ASR_ENABLED=0
PDCA_ASR_PROVIDER=doubao
PDCA_DOUBAO_ASR_URL=https://openspeech.bytedance.com/api/v3/auc/bigmodel/recognize/flash
PDCA_DOUBAO_ASR_APP_KEY=
PDCA_DOUBAO_ASR_ACCESS_KEY=
PDCA_DOUBAO_ASR_API_KEY=
PDCA_DOUBAO_ASR_RESOURCE_ID=volc.bigasr.auc_turbo
PDCA_DOUBAO_ASR_TIMEOUT_SECONDS=180
PDCA_DOUBAO_ASR_MODE=fallback
```

`PDCA_DOUBAO_ASR_MODE`：

```text
fallback   Vemory 无转写或质量低时调用
verify     外部经销商会议同时调用，用于交叉验证
always     所有符合条件会议调用
```

默认 `fallback`，控制成本。

### 10.4 触发流程

```text
Vemory 同步发现会议
  -> 判断 meeting_type 是否经销商会议
  -> 获取 meeting external_id 和音频 URL
  -> 计算 artifact_key
  -> 检查是否已识别
  -> 创建 meeting.asr_requested
  -> 调豆包
  -> 规范化 segments
  -> 写 meeting_asr_artifacts
  -> 创建 meeting.asr_completed
  -> 群 Agent 提取任务、承诺和卡点
```

### 10.5 音频来源

优先顺序：

1. Vemory detail 提供的可访问音频 URL。
2. 服务端下载后提交 Base64。
3. 无音频时标记 `blocked:no_audio_source`。

安全：

- 不在日志打印完整签名 URL。
- 不把密钥、音频、客户原件写入 Git。
- 临时文件使用系统临时目录，用完删除。
- 外部 URL 设短时有效。

### 10.6 说话人和置信度

- ASR 的 `speaker_1` 不自动映射为客户或销售。
- 有参与人和明确自我介绍时才允许模型建议映射。
- 映射置信度低于阈值时标“待确认”。
- 付款、金额、日期、折扣必须从原句二次核验。

### 10.7 重试

- 429、服务繁忙、5xx：指数退避，最多 3 次。
- 参数错误、格式错误：不重试，进入人工队列。
- 超过 2 小时或 100 MB：转标准版或标记人工处理。
- 同一 `audio_sha256` 不重复识别。

## 11. MTO 视觉能力

### 11.1 复用现有实现

优先复用：

```text
app.mto_ocr.review_mto_images
app.mto_ocr.ocr_image_bytes
app.mto_ocr.parse_quote_text

```

现有 Qwen 配置继续有效，不为“Agent”名义重写。

建议新增薄封装：

```text

```

### 11.2 检查顺序

1. 读取当日、指定人员发送的图片。
2. 下载附件。
3. 计算 SHA-256。
4. 检查当日和历史重复图。
5. OCR/视觉识别产品、材质、颜色、报价。
6. 解析人民币金额。
7. 判断单款是否不低于 30 万。
8. 按“不同设计”去重计数。
9. 写结构化结果。
10. 群 Agent只消费结果，不重新看原图猜测。

### 11.3 判定规则

- 图片存在但 OCR 失败：`review_status=pending_manual`。
- 报价缺失：不能算金额达标。
- 同图重复发：只计一次。
- 同款仅改文件名：只计一次。
- 图片内容差异无法确定：人工复核。
- 无视觉密钥：张数可统计，金额达标写“待确认”。

### 11.4 模型调用策略

- 哈希、文件类型、图片数量：标准库处理。
- OCR 可解决时不调用大视觉模型。
- 低置信度、复杂版式再调用视觉模型。
- 单图结果缓存，避免 10/15/20 重复计费。

## 13. 端到端业务流程

### 13.1 用户临时任务

示例：

```text
“查所有人今天有没有向客户铺垫圣诞黑五提前备货”
```

流程：

1. Task Gateway 创建 `agent_runs`。
2. 主 Agent 判断范围：五达标群、C转B 16 群、日报、Vemory、WhatsApp。
3. 生成并校验查询计划。
4. 流程控制器并行采集各数据源。
5. 群 Agent 返回本群事实和缺失项。
6. ASR/Vision仅在任务相关时调用。
7. 主 Agent 汇总。
8. 事实校验器检查关键词、原文、时间、发送人。
9. 输出：
   - 谁明确做了。
   - 谁明确说没做。
   - 谁没有可核查证据。
   - 数据源未覆盖什么。
10. 默认只返回用户，不推群。

严禁把“未检索到证据”写成“该销售一定没说”。

### 13.2 10:00 早追

1. 09:45 采集。
2. GroupGraph 加载昨日未闭环动作。
3. 检查当日群内是否已报 3—5 项。
4. 生成任务和缺失清单。
5. 写 Outbox。
6. 10:00 自动模板或人工批准后发送。
7. 收到认领回复后写 `claimed_at`。
8. 10:05 检查执行链路。

### 13.3 15:00 中追

1. 14:45 采集。
2. 比较 10:00 事实和任务。
3. 更新 `pdca_tasks`。
4. 客户在等回复时优先催回复。
5. 卡政策、车源、报价、技术时生成中台协同任务。
6. 只发变化，不重发全量计划。

### 13.4 20:00 晚追

1. 19:45 采集。
2. 对比 15:00。
3. 核验群消息、WA、Vemory、VPS、日报、MTO。
4. 通过则 `verified -> done`。
5. 不通过则 `rejected/in_progress/blocked`。
6. 未完成生成次日第一动作。
7. C转B 执行当前 20:00 晚追。
8. 扣罚只生成待审批草稿。

### 13.5 经销商会议

1. Vemory 同步会议。
2. 判断是否外部经销商会议。
3. 获取音频和已有转写。
4. 按 ASR 模式调用豆包。
5. 保存转写证据。
6. 提取：
   - 客户承诺。
   - 付款金额和日期。
   - 订单/SKU。
   - 物流和售后。
   - 合同/折扣/权益。
   - 下一动作、执行人、截止时间。
7. 低置信度进入人工复核。
8. 通过后写 `pdca_tasks`。
9. 群 Agent 在下一档跟踪。

### 13.6 MTO 图片

1. 群消息出现图片。
2. 视觉服务识别并缓存。
3. GroupGraph 汇总当日不同设计数。
4. 4 款且每款不少于 30 万才可标达标。
5. 缺报价或识别失败写待确认。
6. 原图和结构化结果一并作为证据引用。

### 13.7 部门总结

主 Agent 输入：

- 五群最新 snapshot。
- C转B 16 人摘要。
- 日报提交与冲突。
- 未闭环 `pdca_tasks`。
- ASR 新增承诺。
- MTO 结果。
- 红黑榜。
- 数据源健康状态。

输出结构：

```text
30 秒结论
昨日已兑现
昨日未兑现
今日第一动作
客户/订单/回款卡点
中台需拍板
C转B战役
数据缺失与待确认
```

实现顺序故意不是先写主 Agent。主 Agent 依赖稳定事实、工具和状态；先写会成为空壳。

### P0：恢复和验证现有调度

目标：先保证现有业务正常。

任务：

- 确认生产 scheduler 常驻。
- 确认 `PDCA_DUZHAN_ENABLED=1`。
- 确认 9:45/10:00 作业可执行。
- 新增 10:05 健康检查。
- 不改变任何三追文案。

验收：

- 当天生成 `asia_shanghai_{date}_10.json`。
- `scheduled_job_runs` collect 和 push 成对。
- 四个北京时间达标群收到消息。
- Alice 只在巴黎 10:00 收到。
- 重启后不重复发送。

### P1：统一事件、Outbox 和审批

目标：建立系统交接层。

任务：

- 创建 `agent_runs`、`agent_events`、`agent_outbox`。
- 扩展 `pdca_tasks`。
- 所有新功能只写 Outbox。
- 现有 push 函数先保留。

验收：

- 同一幂等键只能有一条 Outbox。
- 扣罚草稿未批准不能发。
- 批准、拒绝、重试有 audit log。
- 既有督战测试不回归。

### P2：流程控制器封装

目标：Cron 和 Agent 使用同一业务入口。

任务：

- 新增 `flow_controller.py`。
- `jobs.py` 改为调用封装。
- 不改变 `prepare_duzhan`、`run_duzhan` 输出。
- 增加状态事件和健康检查。

验收：

- 原测试通过。
- 人工调用和 Cron 调用产生相同快照。
- 单群推送失败不阻断其他群。

### P3：单群 GroupGraph 影子运行

目标：验证群 Agent 闭环。

试点：

- 先选张三群或一个测试群。
- `PDCA_AGENT_SHADOW_MODE=1`。
- 只生成草稿和任务，不推群。

任务：

- 实现任务状态机。
- 读取当前和上一档 snapshot。
- 读取 `pdca_tasks`。
- 生成结构化群结果。
- 与现有 `render_brief` 对照。

验收：

- 不编造金额。
- “收到”不闭环。
- 有证据才能 `verified`。
- 15:00 只输出变化。
- 影子草稿不影响生产。

### P4：扩展所有达标群与 C转B

目标：一图多实例。

任务：

- 通过 `channel_id` 隔离 checkpoint。
- 支持时区和语言。
- 接五达标群。
- 接 C转B 16 群 20:00。
- 日报群仅作交叉核对。

验收：

- 21 群状态不串群。
- Alice 英文和巴黎时区正确。
- C转B `None` 不当 0。
- 16 群失败可分别重试。

### P5：MTO 视觉接入

目标：把图片结果变成证据。

任务：

- 封装现有 `mto_ocr`。
- 加 SHA-256 和缓存。
- 将结果写事件和任务 evidence。
- 增加人工复核状态。

验收：

- 重复图只计一次。
- 无报价不算达标。
- 无密钥写待确认。
- 4 款判断可追溯到图片。

### P6：豆包 ASR

目标：经销商会议进入闭环。

任务：

- 创建适配器和 artifact 表。
- 先用脱敏测试音频。
- 接 Vemory 音频来源。
- 支持失败、重试、人工复核。
- 提取结果先影子运行。

验收：

- 相同音频不重复收费。
- 转写含时间戳。
- 低置信度不自动创建确定性承诺。
- 音频不进入 Git。

### P7：主 Agent / LangGraph

目标：统一任务入口和部门总结。

任务：

- 实现结构化决策。
- 工具权限白名单。
- 加事实校验节点。
- 加人工审批 interrupt。
- 接入现有 Hermes chat 或新增 API，二选一，不建两个入口。

验收：

- 能拆分“查全部门圣诞黑五铺垫”。
- 能覆盖五群、C转B、日报、会议。
- 能明确“未见证据”与“明确没做”的区别。
- 模型不可用时定时任务仍正常。
- 主 Agent 不能直接调用 push。

### P8：逐步启用

顺序：

```text
开发环境
-> 测试数据 replay
-> 单群 shadow
-> 五群 shadow
-> C转B shadow
-> 人工审批外发
-> 自动模板外发
```

任何阶段出现串群、重复推送、无证据结论，立即关闭 Agent 开关并回退现有模板。

## 18. 可观测性

必须记录：

- 调度计划时间、实际开始时间、延迟。
- 采集耗时和各数据源状态。
- 每档快照完整度。
- 每群草稿、审批、发送状态。
- LLM 模型、调用耗时、输入/输出 token、错误。
- ASR 音频时长、处理耗时、状态、费用字段预留。
- MTO 图片数、缓存命中、识别失败。
- 任务认领率、证据提交率、按时闭环率。

核心告警：

```text
slot_missing_after_5m
push_failed
duplicate_send_prevented
database_unavailable
source_degraded
asr_failed
vision_failed
approval_overdue
group_state_crossed
```

日志不得包含：

- 完整密钥。
- 完整客户手机号。
- 完整签名音频 URL。
- 客户原始合同全文。

## 20. 部署与回滚

### 20.1 部署

1. 在 `codex/<task>` 工作树开发。
2. 迁移先在测试数据库执行。
3. 默认所有新开关关闭。
4. 部署明确 Git commit。
5. 打开健康检查。
6. 打开 shadow mode。
7. 验证一周。
8. 再开人工审批外发。
9. 最后考虑自动模板外发。

### 20.2 回滚

关闭：

```text
PDCA_AGENT_ENABLED=0
PDCA_SUPERVISOR_ENABLED=0
PDCA_ASR_ENABLED=0
PDCA_AGENT_OUTBOX_ENABLED=0
```

回滚后：

- 现有 `duzhan_job`、`ctob_job`、`daily_report_job` 继续工作。
- 不删除 Agent 表。
- 未发送 Outbox 保留审计。
- 不回滚已经发送的群消息。

## 21. 给执行模型的固定要求

执行模型必须遵守：

1. 每次只做一个阶段。
2. 开始前读取相关现有代码和测试。
3. 优先封装复用，不复制 `duzhan`、`ctob`、`mto_ocr` 逻辑。
4. 不修改无关文件。
5. 不用 `.work/` 脚本代替生产实现。
6. 不使用真实客户数据写测试。
7. 不把密钥、音频、图片、导出文件提交 Git。
8. 新 Python 公共函数必须有清晰 docstring；JavaScript/TypeScript 注释使用 JSDoc。
9. 所有模型输出使用结构化 schema。
10. 所有事实附来源。
11. 数据未知写“待确认”。
12. 外发统一走 Outbox。
13. 扣罚、合同、折扣、规则变更强制人工审批。
14. 未经用户要求不 commit、不部署、不推群。
15. 完成后报告：
    - 修改文件。
    - 数据迁移。
    - 测试命令和结果。
    - 未完成项。
    - 回滚方式。

## 23. 最终 Definition of Done

- 调度常驻，漏跑 5 分钟内告警。
- 主 Agent 能接任务、拆任务、汇总，但不能直接发群。
- 五达标群和 C转B 16 群状态完全隔离。
- 每个业务任务有执行人、截止时间、证据和闭环状态。
- 豆包 ASR 可识别经销商会议并保留来源。
- MTO 图片可去重、识别报价并形成证据。
- 所有外发可审计、可审批、可重试、不可重复。
- 模型停机时，现有三追、日报、C转B 调度仍可运行。
- 所有未知数据明确写“待确认”。
- 所有高风险动作由人工最终决定。
