# 督战官（多智能体督战系统）实现说明

> 版本：2026-09-23 ｜ 仓库：`your-org/duzhan-supervisor` ｜ 应用目录：`pdca-workbench/`
> 用途：把「每天谁该干什么、干到哪了、卡在哪、兑现没有」变成**定时自动推送 + 可追溯证据**的闭环；
> 这份文档可以让另一个人**照着搭一套符合自己需求的督战官**（改数据源、改群、改口径、改档位即可）。

---

## 一、它是什么（目标与成品形态）

### 1.1 解决什么问题

传统销售管理靠「人盯人 + 群里喊」，三个痛点：
1. **不知道**：谁今天该干什么、昨天说的兑现没有，全靠记忆；
2. **追不动**：一件事从「说了」到「做完」中间没人跟，卡点烂在群里；
3. **算不清**：目标 ÷ 天数这种简单算术，人算得又慢又不一致。

督战官的定位：**把管理动作产品化**——每天固定时点，把「目标进度 + 谁做了什么 + 谁没做 + 卡点 + 明日第一动作」自动推到对应的群里，并且**每条结论都能追溯到原话/截图/系统数据**。

### 1.2 成品形态（四条固定输出）

| 时点（北京时间） | 名称 | 发到哪里 | 内容定位 |
|---|---|---|---|
| 工作日 10:00 | 早追·定任务 | 每个业绩达标群（逐人一版） | 定今日 3–5 项 + 目标进度 + 当前卡点 |
| 工作日 15:00 | 中追·追变化 | 每个业绩达标群 | **只报相对 10:00 的变化**（完成/推进/停滞/未回） |
| 工作日 20:00 | 晚追·验兑现 | 每个业绩达标群 | 核对交付物与证据 + 当日总结 + 明日第一动作 |
| 次日 08:00 | 海外渠道日报 | 只发「海外日报群」（汇总） | 总—分结构：大部门 → 小部门 → 个人（覆盖前一自然日 24h） |

另外两条并行输出：
- **C转B 群三档**（10:00/15:00/20:00，规则与达标群同构，文案不同）；
- **08:00 管理类 HTML**：督战证据 HTML（07:00 生成，逐人卡片 + 原图/OCR + 原话）、策略核查 HTML
  （前 24 小时 WhatsApp 逐条策略判定：有 / 部分 / 无 / 无WA / 待确认；栏目与关键词全部来自 `app/wa_strategies.json`，
  换政策只改 JSON，带 `until` 的策略到期自动不再出现在报告里）。

### 1.3 关键设计原则（照抄即可，别踩坑）

1. **缺数据不编 0**：读不出写「待确认」，一笔都没有写「未检索到」——判断类结论必须有原文/截图/系统数据支撑。
2. **同一个时点绝不重复发**：run 台账（claim）+ 推送幂等键双保险（详见第七节）。
3. **推送内容分层**：三档只出「总结性内容」，明细（原话、报价图、OCR）走 08:00 那份 HTML，避免群里刷屏。
4. **员工可见的口径必须统一**：如「已录单（开单额）」= 系统 sales 视图，不是银行回款；改名时三档/日报/HTML 一次改全。
5. **自动化的边界**：机器只负责「取数 + 汇总 + 提醒 + 留证」，**发出去的话必须能被人一眼验证**；不做无人复核的对外承诺。

### 1.4 适用与不适用

- 适用：有固定群、有每日节奏、有可查询的业务系统（销售/回款/客户触达）的团队，人数 5–50。
- 不适用：没有稳定数据源的纯人工团队（建议先做第七节的「人工待办 JSON」形态）。

### 2.2 一次「10:00 定任务」的完整链路

1. **09:45** `duzhan_collect_job` 触发（每档前 15 分钟，避开整点忙）：
   - 四个数据源**并发**拉取：personal-OKR（业绩）、Agent/IM 报告（VPS 留痕）、Vemory（会议）、日报群；
   - **并发**拉取每个达标群/跟进群的历史消息（8 并发）；
   - **并发**拉取每人三项 MCP（WA 触达/经营/客户明细，6 并发）；
   - **并发**跑每人当日图片 OCR（默认 3 并发、单轮 420s 预算，超时写「待确认」）；
   - 组装**台账**（每人一行：目标、已录单、水单、意向、MTO、WA 户数、工时、卡点、证据、日报）；
   - 渲染每个群的正文并**写快照** `data/runtime/duzhan_slots/<tz>_<day>_<hour>.json`（不发群）。
2. **10:00** `duzhan_job` 触发：`claim_run('duzhan', '<tz>:<hour>:<day>')` 占档 → 读快照 → 按群推送 → `finish_run(sent)`。
3. **10:30** `duzhan_backup_job` 兜底：同一 bucket 已被 claim 就跳过；若 10:00 崩溃/漏跑，则用快照补发（VPS 幂等键防重复）。
4. 失败即告警：`notify()`（VPS IM 机器人或 webhook），并在 run 台账留 `failed` + 原因。

### 2.3 三轴分离（改需求时先想清楚改哪一轴）

| 轴 | 内容 | 改动影响 |
|---|---|---|
| **数据轴** | 数据源（IM/MCP/CLI/OCR）、口径（三关键词）、目标表 | 只影响数字，不动文案骨架 |
| **表达轴** | 四档模板、分流规则、红黑榜、第 8 节待办 | 只影响读起来的样子 |
| **投递轴** | 收件人（群/私聊）、时点、兜底、幂等键 | 只影响发给谁、什么时候、会不会重复 |

**约定**：任何一次需求变更，先在 PR 描述里写清属于哪一轴，避免「改文案顺手改了取数」这种事故。

## 四、口径与目标（数字怎么算）

### 4.1 业绩三关键词（员工可见的唯一口径）

| 关键词 | 定义 | 数据来源 | 显示规则 |
|---|---|---|---|
| **已录单（开单额）** | 系统 sales 视图（odoo_sale，**不是银行回款**） | `vertu-cli sales +personal-okr` 的 `sales_amount` | 写具体金额，读不出写「待确认」 |
| **水单** | 客户已付款、尚未到我们账户 | 群消息含「水单」的行（正则抠金额） | 有则列金额+原文，没有写「未检索到」 |
| **意向** | 客户明确表达意向及金额 | 群消息含「意向」的行 | 同上 |

实现：`duzhan_ledger.parse_performance_buckets()` + `_perf_amount()`（金额支持 `$45,000 / 1,200万 / 2000000元` 等写法；**千分位、整万、美元按 7.1 折算**）。

> 口径事故警示：曾把「已录单」叫「累计回款」，导致员工以为在催银行到账。**改名时必须三档+日报+HTML+README 一次改全**，并同步改测试断言。

### 4.2 目标体系

```
部门月目标（department_target_wan）
   └── 个人月目标（按人头）          例：张三 200 万
   └── 小组目标 + members（按组）     例：新部 100 万（成员A/Sofia/成员C/成员D 合计）
```

- **唯一来源**：`app/monthly_sales_targets.json`（由人每月更新）。解析优先级：
  `文件按姓名` → `文件里的小组条目按成员匹配并摊到人` → `代码里 OWNERS 的历史硬编码值`。
- 走到第三步（说明文件没配全）会**告警一次/月**，绝不静默沿用旧数。
- 不变量：**明细合计必须等于部门目标**（`app/daily_report.py` 与 `scripts/set_monthly_targets.py` 都会校验），不一致直接拒绝写盘/报错。
- 维护脚本：`python scripts/set_monthly_targets.py --month 2026-10 --copy-from 2026-09 --dept 1500 --person 张三=260 --group 新部=120:成员A,Sofia,...`（`--dry-run` 先看）

### 4.3 滚动日目标（修掉过「今日目标=月目标」的 bug）

```
日目标     = 月目标 ÷ 当月天数
累计应达   = 日目标 × 已过天数（含当天）
领先/落后  = 已录单 − 累计应达
```

- 边界都覆盖：月初/月末/2 月/闰年/非法日期（返回「待确认」而不是崩）。
- 部门口号「部门月度战役」只是口号（≈部门月目标），**不参与计算**——它曾被错误地当成「今日目标」显示过。

### 4.4 红黑榜（部门口径，全员可见）

- **综合分 = 过程 50% + 业绩 50%**：业绩分 = 达成分（`已录单 ÷ 累计应达 × 100`，封顶 120）；过程分 = 过程完成度（任务闭环、证据、留痕）。
- 两个口径**都必须有**：业绩分缺失时写「业绩待确认」，不能只按过程分排名。
- 榜是**部门口径**，每个群都会看到全部 10 人（老板 2026-09-20 拍板），文案里显式标注「部门口径·全员可见」。
- 黑榜理由只用「读得到的事实」：未报计划、本月已录单 0、WA 未覆盖、证据不足…（长假期间整段豁免，见第八节）。

### 4.5 工时（对照标准 8h）

`工时 = WA 沟通(按聊天跨度估) + MTO 图处理 + 催收跟进 + 会议(Vemory) + VPS 留痕`，与「日报申报工时」**并列显示、互不覆盖**：

```
• 工时（对照标准8h）：6.6h / 标准8h｜近满勤｜WA 3.0h + MTO 1.33h + 催收 1.5h + 会议 0.77h + VPS 0.0h｜缺口 1.4h
• 日报申报：已交，完成 3/5 项；申报 7.5h；系统证据 6.6h；0.9h 待补证
```

**零证据时写「待确认」而不是 0 小时**（`estimate_hours()` 返回 `minutes=None`）。

## 五、消息结构与分流（四档 + 四类收件人）

### 5.1 四类收件人（谁看什么）

| 收件对象 | 收到什么 | 收件人 id 来源 |
|---|---|---|
| 业绩达标群（每人一版） | 三追 10/15/20 档（长版） | `app/duzhan.py: GROUPS`（群 id + 时区 + 语言 + 汇报人） |
| C转B 跟进群（16 个） | C转B 三档 | `app/ctob.py: OWNERS` |
| 海外日报群 | 次日 08:00 汇总（**只有这一档**） | `PDCA_TODO_GROUP_CHANNEL_ID` |
| 督战官管理群 | 07:30 证据 HTML + 08:00 策略核查 HTML | `PDCA_MGMT_HTML_CHANNEL_ID` / `PDCA_CAMPAIGN_WA_CHECK_CHANNEL_ID`（2026-09-23 起只发群，**不再私聊**） |

**原则**：达标群只收到「跟他有关」的内容；管理面的东西（如早会待办里的管理层条目）**只进管理名单**，不往群里丢。

### 5.2 达标群长版（默认形态）逐节说明

```
【海外渠道业绩达标群 · 每日三追进度表】早追·定任务 10:00（北京时间）
- 汇报人：张三 | 日期：2026-09-23 | 阶段：10:00
- 本档动作：每人提交今日 3–5 项工作（对象、交付物、截止时间）；未报则点名催报。
- 月度目标：200 万 | 滚动日目标：6.67 万/天（第 23/30 天，累计应达 153.4 万）｜领先 36.8 万
- 已录单（开单额）：194.2 万 | 战役：部门月度战役

0. 今日目标（本档先定）：日目标 6.67 万/天，累计应达 153.4 万｜领先 36.8 万
   • 昨日未闭环结转（今日第一动作）：…
```

### 6.2 并发与时间预算（这是能准点推送的关键）

`collect_ledger()` 一次采集里：

| 阶段 | 并发度 | 说明 |
|---|---|---|
| 四个数据源（OKR/VPS/Vemory/日报群） | 4 | 各源独立兜底（`_safe_fetch`） |
| 各群历史 | 8 | 群之间互不依赖 |
| 每人三项 MCP | 6 | 同一人的三项在一个任务里顺序执行 |
| 每人 MTO 图片 OCR | `PDCA_MTO_OCR_WORKERS`（默认 3） | 单轮总预算 `PDCA_MTO_OCR_BUDGET_SECONDS`（默认 420s），超时未完成的按「待确认」返回，**不等未完成线程** |
| 每人截图 OCR 上限 | `PDCA_MTO_OCR_MAX_IMAGES`（默认 8 张/人） | 一天几十张图时避免拖过整点窗口 |

实测收益：同数据源串行 ~36.5s → 并发 ~20s（数据日 2026-09-19，10 人）。

**设计要点**：
- `_parallel_map` 保持输入顺序，单项异常只记日志留 `None`；
- 采集源按**名字**取值而不是下标（`fetched["personal-okr"]`），避免将来调整顺序导致 A 的数据接到 B 的字段上；
- OCR 有独立的时间预算（`_parallel_map_deadline`），因为它是唯一的「分钟级」环节。

### 6.3 图片 OCR 的两个用法

1. **MTO 报价图**（`app/mto_ocr.py`）：
   - 下载到临时目录 → OCR → **无论成败立即删文件**；
   - 型号是硬要求：读不出会追问一次（`MODEL_PROMPT`），仍读不出标记 `model_missing`；
   - 输出 `{model, total_usd, wan, delivery, target_customer, qualifies}`，≥30 万才算「达标款」；
   - 金额/型号清洗规则要**保留合法连写**（如 `SampleModel-C4L4PDH99E-2026`、`SampleSignatureS+`），并避免把 `EST` 当成型号边界。
2. **早会待办图**（`app/meeting_todos_fetch.py`）：
   - 从指定私聊取当天图片，**优先最新一张**（汇总图），读不出再回退；
   - 解析 `【负责人】`/`负责人：` 两种写法，去重、跳过「看不清」；
   - 按 OWNERS 别名映射到群（`attach_scope`），映射不到的算管理面。

## 七、可靠性设计（不重复发、不静默失败、不误连生产库）

### 7.1 三层防重复

1. **run 台账（at-most-once）**：`claim_run(job, bucket)` 用唯一 `run_key` 抢档；
   - `sent` → 后续触发全部跳过（兜底档天然不会重发）；
   - `sending` 超 30 分钟视为卡死，可被回收（崩溃/重启后能自愈）；
   - `failed` 允许再认领（网络抖动后可重试）。
2. **推送幂等键**：VPS 推送带 `Idempotency-Key`（如 `duzhan-20260923-1000-<channel8>`、`ctob-20260923-1000-<channel8>`、`evidence-<day>-<user>`）。**同一个键服务端只落一次**，即使本地重发也不产生第二条。
3. **@回复幂等**：回复消息用 `duzhan-at-<message_id>`，并把「已答消息 id」写进游标（**原子写**：先写 tmp 再 `os.replace`，逐条回复后立即落盘）。

> 事故复盘：游标曾出现**读写 schema 不一致**（写 `last_seen`、读 `last_created_at`），导致回复后游标被当空的重置 → 漏答 @ 并可能重答。修法：统一 `_cursor_row()` 构造 + 保持写入顺序 FIFO 截断。**改游标结构必须同时改读写两侧并加回归测试。**

### 7.2 不静默失败

- 每个定时任务：`try/except` → `finish_run(failed, 原因)` → `notify(title, detail)`（VPS IM 机器人或 webhook，相同告警 10 分钟去重）。
- 取数失败**必须**渲染成「待确认」，而不是「0 / 未见 / 没交」：
  - 日报群取数失败 → 「待确认（日报群取数失败）」，且**不扣分**；
  - OCR 无密钥/失败 → 「待确认」（不把图片张数当达标款数）；
  - MCP 非 200 → 记 `error` 日志 + 字段「待确认」。
- 运行凭证与告警都在数据库里可查：`SELECT run_key, status, detail FROM scheduled_job_run ORDER BY started_at DESC`。

### 7.3 环境与安全

| 事项 | 做法 |
|---|---|
| 密钥 | 只走环境变量；`.env` 不入库；日志自动脱敏（`SECRET/TOKEN/KEY` 命中的值记入敏感清单） |
| TLS | 禁止 `verify=False`。Qwen 网关证书由公共 CA 签发 → 走标准校验；换内网 CA 时用 `PDCA_QWEN_CA_BUNDLE` |
| 外部命令 | Windows `.cmd` 经 `cmd /c` 启动会二次解析参数 → 带 `" & | ^ < > %` 的参数直接拒绝（防注入） |
| 子进程 | 超时必须 `kill()` 并 `wait()`（否则「调用方以为失败、副作用命令继续执行」） |
| 本机误操作 | **本机进程直连生产库时，`claim_run` 直接拒绝占档**（`remote_db_from_host` 判定：非容器 + 非本机库）；要放行必须显式 `PDCA_ALLOW_REMOTE_DB=1` |
| 环境变量传递 | 部署脚本把 `.env` 里**全部 `PDCA_*` 透传**进容器，黑名单只排除本机专属项（`PDCA_DATABASE_URL`、`PDCA_SECRET_KEY`、本机路径、`pg_dump` 命令）——避免「本地配了、容器没收到」 |
| 临时文件 | MTO 图片：每张独立临时目录 + `finally` 删除；每小时清理 6 小时前的残留（进程被强杀时的兜底） |
| 附件命名 | 发送前净化：统一 `\`→`/`、取 basename、去点前缀、白名单字符 |

### 7.4 幂等与并发的边界

- 并发只用于**只读采集**；写操作（推送、写游标、落盘）都在主线程串行，且各自带幂等/原子写。
- 单进程内 `max_instances=1` + `coalesce=True`：同一任务不会并行两份。
- 多副本部署**不支持**（scheduler 会在每个副本各跑一遍）——要保持单副本；需要高可用时改「独立调度进程 + 多 worker」架构。

## 八、工作日与休假日历

### 8.1 三种日子

| `day_kind` | 定义 | 推送 | 处罚 |
|---|---|---|---|
| `workday` | 周一~周五且非法定假日 | ✅ | ✅ 正常 |
| `makeup` | **周末但调休上班** | ✅ | ✅ 正常（调休**不豁免**） |
| `long_holiday` | 长假区间（≥3 天） | ✅ | ❌ **不处罚**（不列黑榜、不记扣罚） |
| `rest` | 法定假日或普通周末 | ❌ | — |

### 8.2 数据源与维护

`app/holidays_cn.json`（**人工维护，每年国务院办公厅通知发布后更新一次**）：

```json
{
  "2026": {
    "holidays":  {"2026-09-25": "中秋节", "2026-10-01": "国庆节"},
    "workdays":  {"2026-09-20": "中秋/国庆调休补班"},
    "long_holidays": [
      {"name": "中秋节", "start": "2026-09-25", "end": "2026-09-27"},
      {"name": "国庆节", "start": "2026-10-01", "end": "2026-10-07"}
    ]
  }
}
```

- **缺年份不编造**：没配置的年份退回「周一~周五 = 工作日」，并且每年只告警一次提醒补数据。
- 长假阈值按老板口径：**3 天以上算长假**。
- 用途：`is_duzhan_workday()` 决定推不推；`penalty_exempt()` 决定处不处罚；`calendar_note()` 生成正文提示。

### 8.3 为什么必须把 cron 写成「每天都触发」

早期实现把三追的 cron 写成 `day_of_week="mon-fri"`，结果：
- **周末调休上班日永远不推**（cron 根本不触发）；
- **落在周末的长假档也永远不推**。

正确写法：cron `day_of_week="mon-sun"` + **任务内部**用日历判断跳过。这样调休、长假、法定假日全部由数据（而不是 cron 表达式）决定。

## 九、部署与发布

### 9.1 发布流程（当前实践）


### 9.2 环境矩阵（本机 vs 容器，别混）

| 维度 | 云端容器 | 本机 |
|---|---|---|
| OS / Python | Debian 13 / 3.12.14 | Windows / 3.12.x |

## 十一、照着做：搭一个符合自己需求的督战官

> 目标：**当天能跑起来的最小闭环**，再按需加料。下面按「必须 / 可选」分层。

### 11.1 最小可用版本（MVP，半天到一天）

**要准备的三样东西**
1. **一个能发消息的机器人**（或你自己的 IM 通道）：拿到 `app_id/secret` 与目标群 id；
2. **一份人员清单**：每人 = 显示名 + 所在群 + 在业务系统里的标识（员工号/登录名）；
3. **一份月度目标表**：`{部门合计, 每人/每组目标}`（合计必须等于部门合计）。

**改造点（只改这 4 个文件）**

| 文件 | 改什么 |
|---|---|
| `app/duzhan_ledger.py: OWNERS` | 你的人：`display`（群里叫法）、`group`（群名）、`employee_id/im_user_id`、`vps_names`（别名）、`target_wan`（兜底目标）、`follow_channel_id`（跟进群） |
| `app/duzhan.py: GROUPS` | 你的群：`name`（与 OWNERS.group 对齐）、`channel_id`、`tz`（时区）、`lang`、`reporter`（谁汇报） |
| `app/monthly_sales_targets.json` | 你的目标（先只填一个部门 + 几个人） |
| `app/config.py` 默认值 或 `.env` | `PDCA_DUZHAN_TIMES`、`PDCA_TODO_GROUP_CHANNEL_ID`、`PDCA_MGMT_HTML_USER_IDS`、模型/机器人凭据 |

**把它跑起来**
```bash
# 1) 起库与容器（或本地直接跑）
cp .env.example .env         # 填 DB / 机器人 / 模型凭据
docker compose up -d --build # 或：python run.py（本地调试）

# 2) 先"只组表不推送"，肉眼验收文案
python -c "from app.duzhan import prepare_duzhan; print(prepare_duzhan('Asia/Shanghai', 10))"
# 快照落在 data/runtime/duzhan_slots/<tz>_<day>_10.json

# 3) 验收通过后开推送（.env: PDCA_DUZHAN_ENABLED=1）并确认台账
# SELECT run_key, status FROM scheduled_job_run ORDER BY started_at DESC;
```

### 11.2 常见改法（按需求对照表）

| 你的需求 | 改哪里 | 注意 |
|---|---|---|
| 换成自己的群/更多人 | `GROUPS` + `OWNERS`（两边 group 名一致） | 群 id 变了要同步 `_channel_id()` 的匹配 |
| 改档位时间（如 09:00/14:00/19:00） | `PDCA_DUZHAN_TIMES` | 采集自动提前 15 分钟 |
| 三档输出太长/太短 | `PDCA_DUZHAN_COMPACT` | 长版含 0–8 节；精简版只出总结 |
| 换业绩口径（比如按「毛利」而非「录单额」） | `parse_performance_buckets()` + `_perf_amount()` + 文案里的标签 | 三档/日报/HTML/测试一起改 |
| 目标不按月，按季度 | `daily_target_progress()` 的「按月天数」改成分母配置 | 保持 `None` 时输出「待确认」 |
| 加一节自己的内容（如库存/物流） | `_slot_sections()`（长版）与 `_compact_body()`（精简版） | 空数据时必须整节不出现 |
| 加一类收件人（如区域经理版） | `im_files.send_files()` 的收件人 + `scope` 分流（照 `meeting_todos` 的模式） | 别把管理面内容发进员工群 |
| 接自己的数据源 | 在 `collect_ledger()` 加一个 `_safe_fetch` 源 + `PersonRow` 加字段 | 失败必须「待确认」，不许填 0 |
| 换 IM 通道（企业微信/钉钉/飞书） | `app/vps_im_push.py`（推送）+ `app/vertu/client.py`（读消息） | 幂等键要保留，否则重试会重复发 |
| 换图片 OCR 模型 | `app/mto_ocr.py`、`app/meeting_todos_fetch.py` 里的 Qwen 调用 | 保留「读不出写待确认」与「下载即删」 |
| 不想写代码，只想要「人工待办」 | 直接维护 `app/meeting_todos.json`（第 8 节数据源） | 参考第五节 5.4 的分流规则 |

### 11.3 建议的上线顺序（避免一上来就翻车）

1. **影子模式**：只 `prepare_duzhan()` 出快照 + 把快照贴给自己看，不推群（1~2 天）；
2. **只推一档**（10:00）到一个群，观察 2 天；
3. 补 15:00/20:00，再补 08:00 汇总；
4. 打开兜底与告警（+30 分钟档、`notify`）；
5. 最后接 07:00 证据 HTML 与 08:00 核查（这两个是「可追溯性」的关键，别省）。

### 11.4 交付检查清单

- [ ] 每个群每个人都能收到**只有自己那版**的消息；
- [ ] 读不到的数据一律显示「待确认 / 未检索到」，**没有任何一处把空值渲染成 0**；
- [ ] 同一时点重跑不会重复发（`claim_run` + 幂等键都在）；
- [ ] 失败会告警，且 `scheduled_job_run` 里能看到 `failed` 与原因；
- [ ] 目标表有「合计 = 部门目标」的校验；
- [ ] 有日历（调休/长假），且长假期间不处罚；
- [ ] 有回归测试：文案口径、目标算术、幂等/游标、并发接线。

### 12.2 故障对照表

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 某档整档没发 | 容器在「采集窗口」被重启/部署；上游全挂 | 看 `duzhan_collect:*` 台账状态；用 +30 分钟兜底档或手动 `run_duzhan(tz, hour, now=<当天该档>)` 补发（幂等安全） |
| 群里出现两条同样的消息 | 同一档被两个进程触发 | 检查是否多副本运行；核对幂等键是否缺失 |
| 大量「待确认」 | MCP/CLI/IM 凭据过期；OCR 未配密钥 | 看 `AINativeSales 非 200`、`MTO 附件下载失败 status=401` 等日志；换凭据 |
| 数字全 0 | 取数失败被当成 0 | **这是 bug**：检查是否有人把 `None` 写成 0；回归测试会拦 |
| @回复不响应/重复回复 | 游标文件损坏或被重置；幂等键缺失 | 看 `data/runtime/duzhan_at_cursor.json`；确认回复带 `duzhan-at-<id>` |
| 目标显示不对 | 目标表没更新当月 | 会推送「月度目标未更新」告警；用 `scripts/set_monthly_targets.py` 更新 |
| 长假日推了但没处罚 | 正常 | 长假豁免是设计 |
| 本机跑脚本报「拒绝占用档位」 | 生产库护栏生效 | 只读调试别占档；确需连生产加 `PDCA_ALLOW_REMOTE_DB=1` |
| 证据 HTML 只留 14 天 | 保留策略 | 归档靠每周一 09:00 的备份提醒（人工） |

### 12.3 已知限制（诚实的边界）

1. **单副本**：调度器不做分布式选主，多副本会重复跑。
2. **OCR 依赖单机推理网关**：并发/预算必须设上限；图片特别多的一天（>40 张）可能触发预算截断，剩余图片写「待确认」。
3. **CLI 是外部依赖**：`vps-work`/`vertu-cli` 改名或改路径会让所有取数失败（本项目已踩：CLI 从 `vertu-cli` 改名 `vps-work`）。解析顺序已做兼容，但仍要关注上游变更。
4. **IM 撤回**：机器人发出的消息**无法撤回**（服务端只允许撤回自己发送的消息，且机器人身份接口 401）。**发错只能靠"发之前先审"**——这也是我们坚持「对外内容先出草稿」的原因。
5. **证据 HTML 带图会到 1MB 级**：目前不压缩（老板拍板），保留期 14 天，靠人工归档。
6. **本机与生产库同源**：`.env` 直连生产库是给本机备份任务用的，护栏只拦住「占档/外发」，不拦只读查询——本机别跑写操作。
7. **测试里有部分用例走真实网络**（如 `test_duzhan` 的现场采集用例），本地跑一轮要十几分钟；CI 里是模拟的。

## 附：一句话总结

**督战官 = 定时采集（多源并发 + 失败留白）+ 口径化渲染（目标/进度/证据/待办）+ 幂等投递（claim + 幂等键）+ 可追溯（证据 HTML）+ 人日管理（调休/长假）。**
把它跑起来的关键不是代码量，而是三件事：**口径先定死、缺失值不许编、发送必须幂等。**
